# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Repository layout

This repo is the NestJS (TypeScript) backend itself — `src/`, `test/`, and `package.json` live at the repo root. The frontend is a sibling repo at `../al-yahya-restaurant-frontend` (see that repo's own CLAUDE.md); this backend has no knowledge of it beyond `APP_URL` (see Environment below).

Single-tenant: this serves exactly one restaurant. No multi-tenancy, no per-company scoping anywhere in the schema.

## Commands

Run from the repo root:

- `npm run start:dev` — watch mode (port 3001, overridable via `PORT`)
- `npm run build` — compile with `nest build` → `dist/`
- `npm run start:prod` — run the compiled build
- `npm run lint` / `npm run format`
- `npm run test` (Jest, `*.spec.ts`) — single file: `npm run test -- app.controller.spec.ts`; by name: `npm run test -- -t "test name"`
- `npm run test:e2e`

Database (TypeORM migrations — `DB_SYNCHRONIZE` is `false`, schema changes always go through a migration, never auto-sync):
- `npm run migration:generate -- src/database/migrations/DescriptiveName` — diffs entities against the DB and writes a migration. **Check the generated file before running it** — for anything already holding data, prefer rewriting a generated `DROP COLUMN`+`ADD COLUMN` pair into an in-place `MODIFY COLUMN` (TypeORM's generator defaults to the destructive form even for a plain type-widening change).
- `npm run migration:run`
- `npm run seed` — idempotent (upserts by unique key): loads the full permission catalog, the 6 system roles (with bilingual descriptions), the 3 system taxes, grants Super Admin/Admin every permission, and bootstraps the initial Super Admin user from `SUPER_ADMIN_*` env vars (only if that email doesn't already exist). Safe to re-run any time the permission catalog/system-role/system-tax definitions change — never touches a role's already-configured permissions for non-system roles, and never touches a CUSTOM tax.

## Architecture

Standard NestJS module structure under `src/modules/`: `auth`, `users`, `roles`, `permissions`, `locations`, `company`, `taxes`, `configuration`, `payment-methods`, `categories`, `brands`, `products`, `registers`, `customers`, `sales`, `storage`, `mail`. `src/common/` holds cross-cutting guards/decorators; `src/database/` holds the data source, migrations, and `seed.ts`.

### Auth & sessions

JWT access token (short-lived, `JWT_ACCESS_EXPIRES_IN`) + rotating opaque refresh token (raw random token, only its hash stored in `refresh_tokens`; reuse of an already-rotated token revokes every session for that user — theft detection). The access token payload is deliberately minimal (`{sub}` only) — role/permissions are always resolved fresh from the DB in `JwtStrategy.validate()` via `UsersService.findAuthProfile()`, never cached in the token itself.

`GET /auth/me` returns the caller's profile (id/name/role/permissionCodes) — this is what the frontend's BFF calls right after login to build its own session cookie; nothing else in this backend depends on it.

Password reset and first-time invitation share one mechanism: `User.passwordResetTokenHash`/`passwordResetTokenExpiresAt` + `POST /auth/accept-invitation {token, password}` consumes it either way (`UsersService.setPassword` activates a PENDING user or just updates an ACTIVE one's password — same code path). `POST /auth/forgot-password` only *issues* a fresh token for an existing ACTIVE user; it always returns success regardless of whether the email exists, to avoid account enumeration.

### RBAC model

One role per user (`User.roleId`, not an array — this is intentional, not a v1 limitation). `RoleType` is `SUPER_ADMIN | ADMIN | DEFAULT | CUSTOM`. `PermissionsGuard` (`common/guards/permissions.guard.ts`) is deliberately dumb — it only ever compares `request.user.permissionCodes` against `@RequirePermissions(...)` metadata; Super Admin/Admin pass because they're *seeded* with every permission code (by `seed.ts`), not because the guard special-cases their role type. All the "who can do what to which role" business rules (only Super Admin creates/deletes CUSTOM roles, Admin/Super Admin's own permissions can't be edited, etc.) live in `RolesService`, not the guard — read the comment at the top of that file before changing role-related authorization.

**Permission catalog vs. enforcement — these are deliberately decoupled.** `permission-catalog.ts` lists the *full* target permission set for every module (POS, Customers, Products, Stock, Purchases & Suppliers, Expenses, Accounting, Dashboard, Reports, Settings — 73 permissions total as of the last catalog update), matching the intended final product design. Most of these are **not enforced anywhere yet** — `@RequirePermissions()` only guards routes that actually exist (currently: users, roles, permissions, locations, company, taxes, configuration, payment methods, products, categories, brands, registers, customers, sales). A permission existing in the catalog and being toggleable in the frontend's Roles & Permissions UI does not imply its feature is built; it becomes real only when that module's endpoints are built and start checking it. Don't treat an unguarded permission as a bug — check whether the corresponding feature module exists first. Note `settings.financial_settings` already covers taxes/payment methods/inventory config, and `settings.general_account_setup` covers company overview/custom fields — check for an existing catalog entry before adding a new permission code for a new Settings sub-feature.

### TypeORM gotcha (real bug, already fixed once — don't reintroduce it)

Entities that have **both** a raw `@Column()` for a foreign key and a `@ManyToOne` + `@JoinColumn` relation mapped to that same column (e.g. `User.roleId` + `User.role`) must keep both in sync when mutating. If a relation is eager-loaded (or was joined by an earlier `findOne`) and you only reassign the raw FK column (`user.roleId = newId`), TypeORM's `save()` persists based on the **loaded relation object**, not the raw column, and silently writes back the *old* value. Always update both together: `user.roleId = newId; user.role = newRoleEntity;`. This bit `UsersService.update()` for role reassignment; check any future direct FK mutation on an entity with a paired eager relation for the same issue.

### i18n

`nestjs-i18n`, catalogs under `src/i18n/{en,ar}/*.json` (one file per module: `auth`, `users`, `roles`, `locations`, `company`, `taxes`, `configuration`, `payment_methods`, `products` (also holds category/brand messages), `validation`). Resolved via `?lang=`, `x-lang` header, or `Accept-Language` — the frontend always sends `x-lang` explicitly. When adding a new user-facing error message, add both locale entries; don't hardcode English strings in a service (a few older ones exist as tech debt, e.g. some `BadRequestException` messages — don't copy that pattern for new code).

### Environment gotcha

`APP_URL` is the **frontend's** URL, not this API's — it's used only to build links inside emails (invite/reset) that a browser opens against the Next.js app, not this server. Mixing this up breaks every email link (this happened once already).

### Naming

`User` and `Role` both have bilingual `nameEn`/`nameAr` columns, not a single `name`. `Location` has a single `name` plus `isDefault` (`LocationsService` enforces exactly one default at a time; deleting the default location is rejected). `Role` also has bilingual `descriptionEn`/`descriptionAr` (nullable — only the 6 system roles are seeded with one; a CUSTOM role's description is optional at creation).

### File storage (Firebase, not local disk)

Every uploaded file (currently: the company logo) goes through `src/modules/storage/firebase-storage.service.ts` — a thin wrapper around the Firebase Admin SDK, not `multer` + local disk. Two things to know before touching it:
- URLs are Firebase's own download-token format (`firebasestorage.googleapis.com/v0/b/<bucket>/o/<path>?alt=media&token=<token>`), not a plain GCS public-ACL URL. This is deliberate: newer Storage buckets have "uniform bucket-level access" on by default, which makes `file.makePublic()` fail outright, and it matches this project's existing Firebase convention (there are other objects already in the bucket using this format).
- Credentials (`FIREBASE_PROJECT_ID`/`FIREBASE_CLIENT_EMAIL`/`FIREBASE_PRIVATE_KEY`/`FIREBASE_STORAGE_BUCKET`) live in `.env` only, never `.env.example` with real values. `FIREBASE_PRIVATE_KEY` keeps its PEM's literal `\n` sequences in the `.env` file (double-quoted); the service `.replace(/\\n/g, '\n')`s it at read time.

Any new feature that uploads a file should reuse `FirebaseStorageService`, not reimplement multer/disk logic.

### Public (unauthenticated) endpoints

The global `JwtAuthGuard` requires a valid access token on every route unless `@Public()` is applied (see `common/decorators/public.decorator.ts`) — used today for the auth-establishing routes (`login`/`refresh`/`accept-invitation`/`forgot-password`) and `GET /company/branding`. That branding endpoint is deliberately a separate, narrower route from the full `GET /company` (which stays behind `settings.general_account_setup`) — it exists specifically so the frontend can brand its sidebar and browser-tab favicon even on the pre-login screen, returning only `{name, logoUrl}`. Follow this pattern (a narrow public projection, not loosening the real endpoint) if another feature needs something visible pre-login.

### Taxes: system vs. custom, locked vs. toggleable

`Tax.type` is `SYSTEM_LOCKED | SYSTEM_TOGGLABLE | CUSTOM` (`src/modules/taxes/tax-type.enum.ts`) — this is **not settable through the API**; `POST /taxes` always creates `CUSTOM` (always active, no status toggle, freely editable). `SYSTEM_LOCKED` (`Not Subject to Tax`, `VAT`) and `SYSTEM_TOGGLABLE` (`VAT + Tobacco Tax`) only ever come from `seed.ts`, are never editable (`TaxesService.update()` rejects non-`CUSTOM`), and only `SYSTEM_TOGGLABLE` can have its `isActive` flipped (`TaxesService.updateStatus()` rejects everything else). This mirrors Rewaa's own reference behavior, not an arbitrary design choice — check a fresh screenshot before assuming a new tax-related field should be editable.

A tax has one or more `TaxLine`s (label + rate, summed for the "subtotal") plus an optional single compound line (`Tax.compoundLabel`/`compoundRate`, gated by `Tax.hasCompoundTax`) that applies **on top of** the subtotal (tax-on-tax), not alongside it: effective rate = `subtotal + compound + subtotal*compound/100`. Don't just sum all rates flat when computing anything tax-related later.

### Configuration (Settings → Configuration)

Single-row `configuration` table (`ConfigurationService.findOrCreate()`, VAT as the initial default tax), all routes behind `settings.financial_settings`: `GET /configuration`, `GET /configuration/location-options` (narrow `{id, name}` of active locations), and one `PATCH /configuration/{tax,location,weighted-product,shipping,payment}` per UI card. Default location is **not** stored here — `PATCH /configuration/location` moves `Location.isDefault` via `LocationsService`. Tax rules, split between both services: the default tax must be active; while "VAT + Tobacco Tax" (`SYSTEM_TAX_CODES.VAT_TOBACCO`) is active, sell tax status must be EXCLUSIVE (`TaxesService.updateStatus()` forces it on activation, and `updateTax` rejects INCLUSIVE); a tax can't be deactivated while it's the configured default. `defaultPaymentMethodId` is a `payment_methods` row id (initially Cash). Cost tax status and the weighted-barcode decimal digits (3) are constants in the response, not columns. `seed.ts` no longer resets a SYSTEM_TOGGLABLE tax's `isActive` on re-run — only sets it on first insert.

### Payment methods & bank accounts

`src/modules/payment-methods/` serves both `/payment-methods` (GET/POST/PATCH — **no DELETE**, sales will reference them) and `/bank-accounts` (GET/POST), all behind `settings.financial_settings`. `PaymentMethodType` is `CASH | CARD | BANK_TRANSFER | OTHER`; `PaymentMethodsService.resolveBankAccountId()` forces `bankAccountId = null` for CASH and requires an existing bank account for every other type. Names are unique; bank account numbers are unique. Rows with a `systemCode` (`system-codes.ts`: Cash, Credit Card, and the "Other Bank Accounts" bank account) are created by the `AddPaymentMethods` migration and re-ensured create-if-missing by `seed.ts` (never overwritten — their name/description/link are user-editable); a system payment method's `type` can't change. `PaymentMethod` has both `bankAccountId` and a `bankAccount` relation (for the FK only, never loaded) — always mutate the raw column (see the TypeORM gotcha above).

### `@RequireAnyPermission` (any-of) alongside `@RequirePermissions` (all-of)

`PermissionsGuard` also reads `@RequireAnyPermission(...)` metadata — pass if the user has *at least one*. Used where two flows share an endpoint (product image upload, SKU generation, inline brand creation: `products.create` **or** `products.edit`). The guard is still just set comparison — no role special-casing.

### Products

`src/modules/products/`: `Product` (main product) → `ProductVariant` (SKU/barcode/cost; SIMPLE & COMPOSITE have exactly one, VARIABLE one per option combination — `optionValues` in option order) → `VariantLocation` (per-location quantity, retail/wholesale/buy price, tax; unique per variant+location, a missing row = zero stock/no price). Plus `ProductOption` (VARIABLE), `ProductImage` (Firebase URLs, uploaded first via `POST /products/images`), `CompositeComponent` (COMPOSITE → other non-composite variants, `RESTRICT` so a used variant can't vanish). `ProductType` is fixed after creation. All type-shape rules live in `ProductsService.validateShape()`; SKUs and barcodes share one namespace (unique across both columns). Updates are whole-product replacements: variants matched by `id`, missing ones deleted (rejected if used in a composite), SKUs parked on temp values first so swaps don't hit the unique index.

**Per-user field trimming** — `ProductViewer` (`product-viewer.ts`), built per request from the caller's permissions + assigned locations: without `products.view_cost` responses omit `cost`/`buyPrice` and writes ignore them; without `stock.access` responses omit `quantity`, and with it only the user's locations (unless `allLocations`) are shown/settable. `quantity` and `cost` are only ever set when a variant is *created* (initial values) — the edit path never changes them; future stock operations/purchases own them. COMPOSITE cost (Σ component cost × qty) and per-location "max to sell" are derived on read, never stored. `GET /products` (list), `GET /products/form-options`, and `GET /categories` are all gated `@RequireAnyPermission('products.access', 'pos.access')`, not `products.access` alone — the Sell Screen's product grid and category rail read these same endpoints, and a Cashier role legitimately has `pos.access` with zero `products.*` permissions (a real bug, caught from a live "Something went wrong" on `/pos`: these routes 403'd for an actual Cashier test user before this fix). `GET /products/:id` (single-product detail, only used by the admin product page) stays `products.access`-only. `GET /products/form-options` is a narrow projection (locations, active taxes, Configuration's default tax/tax status/shipping units) so product *and* POS users don't need `settings.*`. Categories (`POST` needs `products.manage_categories`) and brands (`POST` needs create-or-edit) are separate small modules; both `GET`s need `products.access`.

### Categories: hierarchical (parent → child → sub-child)

`Category` (`src/modules/categories/`) has `parentId` (self-referencing, `ON DELETE RESTRICT` — a category with children can't be deleted) and `description`, capped at `MAX_CATEGORY_DEPTH = 3` (checked in the service by walking the `parentId` chain, not a DB constraint). Sibling names (same `parentId`, including two top-level categories both with `parentId IS NULL`) must be unique — enforced in `CategoriesService`, not a DB unique index, since MySQL treats every `NULL` in a unique index as distinct and can't express "unique among top-level categories" on its own; the old flat `UNIQUE(name)` index was dropped in `AddCategoryHierarchy`.

`POST /categories` (individual) takes an optional `parentId` and an optional `assignProductIds` (assigns those products to the new category in the same transaction — "Create category & assign"). `POST /categories/tree` takes `{parentName, children}`: `parentName` finds-or-creates a *top-level* category (that's depth 1), and `children`/their own `children` (depths 2–3) are always newly created, recursively, inside one transaction — a depth or duplicate-sibling-name violation partway through rolls back everything the call had created so far. `PATCH /categories/:id/assign-products` and `PATCH /categories/unassign-products` (→ `categoryId: null`) bulk-(un)set `Product.categoryId`; all of the above need `products.manage_categories`. `GET /categories` (`products.access`) additionally returns each category's computed `depth` and `productCount` (direct children products only, not descendants') for the frontend to build a tree and render counts without extra requests. `QueryProductsDto.uncategorized` (on the existing `GET /products`) filters to `categoryId IS NULL`, mutually exclusive with `categoryId` — this is how Category Management's "Uncategorized" bucket reuses the main products list endpoint instead of needing its own.


### Products: CSV export/import, bulk pricing

Same controller, three more routes (declared before `:id` so Nest doesn't match them as an id): `GET /products/export` (`products.export`) streams a CSV — built with `common/utils/csv.util.ts` (hand-rolled RFC-4180-ish encode/decode, no dependency added), reusing `buildListQuery()`'s filters but capped at `MAX_EXPORT_ROWS` instead of paginated, and respecting the same `ProductViewer` trimming as the list. `POST /products/import` (`products.create`) parses a CSV of SIMPLE products only and calls `create()` per row inside a try/catch, so each row gets exactly the same validation a manual save would (no separate validation path to keep in sync) — a row can succeed with a warning (category/tax name didn't match anything, left blank) or fail outright (missing name/SKU, duplicate identifier, etc.), reported per-row, nothing persisted for a failed row. `PATCH /products/bulk-pricing` (`products.edit`) edits retail/wholesale/buy price, tax and re-order point for many variants at one location in one call, touching only the fields present on each item — built specifically so the frontend's bulk-edit screen doesn't have to resend (and risk overwriting) a whole product just to change its price.

### Registers (POS)

`src/modules/registers/`: `Register` (settings — name, `cashiers`/`paymentMethods` M2M via join tables, `printerType`, a `sellLayout` enum with exactly one value today) is separate from `RegisterSession` (one open→close instance — `openingAmount`/`openingDenominations`, and on close `closingAmount`/`closingDenominations`/`expectedAmount`/`difference`). A register has at most one `OPEN` session at a time (checked in the service, not the schema). `CashMovement` (`IN`/`OUT`, an open session's Add/Withdraw entries) feeds cash's expected amount.

Permission split: `pos.manage_sale_settings` for `POST/PATCH /registers` (creating/editing a register's settings); `pos.access` for open/close plus `RegistersService.assertIsCashier()` (only a register's assigned cashiers may operate it — checked in the service on top of the route guard, same pattern as `ProductViewer`'s permission-driven trimming elsewhere in this codebase); `pos.access` **and** `pos.manage_cash` together for cash movements; `pos.manage_cash` alone for Cash Management (`/registers/sessions*` — a cross-register reconciliation view, not tied to any one register's cashier list). `GET /registers` returns everything grouped by location (`LocationRegisters[]`) — that's the shape the frontend's Registers page renders directly, tab-per-location; each payment method ref now also carries `type` so the frontend's Close Register form knows which one is cash (and needs a denomination breakdown) versus a plain counted-amount input.

**Close Register reconciles every payment method assigned to the register, not just cash** — `CloseRegisterDto.counts` is one `{paymentMethodId, countedAmount, denominations}` per assigned method (denominations only meaningful for the cash-type one); the service rejects a close that omits a method, includes an unassigned one, or double-counts one (`registers.count_every_payment_method` / `registers.duplicate_payment_method_count`). For each method, `expectedAmount` is `openingAmount + Σmovements + Σthat method's COMPLETED sales in this session` for the cash-type method, or just `Σthat method's sales` for every other method — resolved via a `SUM(sale.amountPaid) GROUP BY sale.paymentMethodId` query scoped to `sale.registerSessionId`. Each method's breakdown is persisted as a `RegisterSessionPaymentSummary` row; the session's own `closingAmount`/`expectedAmount`/`difference` are just the sums across methods (the "Total" row in Cash Management).

**Cash Management** (`GET /registers/sessions`, `/registers/sessions/:id`, `/registers/sessions/:id/movements`, `/registers/sessions/export`) is the cross-register, cross-location reconciliation view — every session, open or closed, with a derived `status: OPEN | BALANCED | UNBALANCED` (`RegistersService.sessionStatus()`; a closed session is BALANCED when `|difference| < 0.01`). That epsilon comparison is applied **in the SQL query itself** (`ABS(session.difference) < :epsilon`), not as a JS `.filter()` after pagination — filtering after `.skip()/.take()` would desync `total`/page contents from what's actually returned, a bug caught before shipping. `listMovementsForSession()` (unlike the pre-existing `listCashMovements()`, which requires an `OPEN` session) works for a closed session too, since Cash Management's Add/Withdraw tab is just history at that point. Static routes (`sessions`, `sessions/export`) are declared before the dynamic `sessions/:id`/`:id` routes, per the usual NestJS ordering rule.

### Customers

`src/modules/customers/` — flat entity (no company/account hierarchy). `code` is unique and auto-generatable (`GET /customers/generate-code`, a random 7-digit number, same pattern as a product's `generate-sku`). `update()` builds its patch field-by-field, only including a key the caller actually sent (`optionalFields()`) — a real bug caught in review before shipping: a naive `dto.field ?? null` on every optional column would silently null out, say, `email` on a PATCH that only touches `name`. `POST /customers/quick` (name + phone only, `pos.access`) backs the POS "Add Customer" modal's inline "+"; `GET /customers/search` (also `pos.access`, not `customers.access`) backs that same modal's search box, since a cashier with no Customers-module access at all still needs to attach a customer to a sale. `CustomerListItem.totalPaid`/`debitAmount` are hardcoded 0 — computing them for real needs `Sale.amountPaid` aggregation (doable now that `SalesModule` exists, just not wired up yet) and a receivables ledger (`customers.manage_settlements`, not built) respectively.

### Sales: checkout, park/resume, Invoice List

`src/modules/sales/`: `Sale` (one row per POS transaction; `PARKED` = a "Pause Sale" cart with no `invoiceNumber` yet, `COMPLETED` = a finished, numbered invoice — no void/return status, that's Return Invoices' job when it exists) and `SaleLine`, which **snapshots** `productName`/`sku`/`unitPrice`/`taxRate` at add-time so a later catalog price/tax change never rewrites sale history and so resuming a parked sale needs no product re-fetch. `src/modules/taxes/tax-calculation.util.ts` holds the actual tax math (`effectiveTaxRate()` — the compound-tax formula documented on the Tax entity; `computeLineTax()` — handles `sellTaxStatus` INCLUSIVE vs EXCLUSIVE), shared so it's never duplicated.

**`SalesService.resolveLines()` never trusts a client-submitted price** — it always re-loads the true `VariantLocation` row for the register's own `locationId` and uses its retail/wholesale price and assigned tax; `unitPriceOverride` on a line is only honoured for a caller with `pos.edit_prices_discounts` (checked in `assertLinePermissions()`, independent of what the route guard alone would allow), same for any sale-level discount, and `sellAt: WHOLESALE` needs `pos.sell_wholesale`. Only full payment is supported (`amountTendered >= total` required) — `pos.checkout_post_payment` exists in the catalog for a future deferred-payment flow but **isn't wired to anything yet**; don't add it as a guard on the checkout route itself, that would block every ordinary cashier (a mistake caught and fixed during this build).

**Stock**: a SIMPLE/VARIABLE line decrements its own `VariantLocation.quantity`; a COMPOSITE line decrements its **components'** stock instead (a composite never holds its own — see the Products section above), expanded via `resolveStockDeductions()` and aggregated per variant before `applyStockDeductions()` checks sufficiency and writes, inside the same transaction as the `Sale`/`SaleLine` rows. Insufficient stock, an unassigned payment method, a closed register, or a non-cashier caller all reject the whole checkout — **unless** `SaleSettings.sellWhenQuantityZeroOrBelow` is on, in which case `applyStockDeductions()` skips the sufficiency check entirely and lets an existing `VariantLocation.quantity` row go negative (a variant with no stock row at all is still always rejected — the setting lets a real balance go negative, it doesn't fabricate one from nothing).

**Invoice numbers** (`S{YYYYMMDD}-{n}`) are assigned only on `COMPLETED`, via `nextInvoiceNumber()` counting that day's already-completed sales — not race-proof under heavy concurrent checkouts on the same day (no dedicated sequence table), acceptable for a single-tenant restaurant's realistic throughput.

`GET /sales` also accepts `registerSessionId` — Cash Management's "Session Invoices" button filters the same Invoice List query down to one register session. Both `GET /sales` and `GET /sales/:id` accept `pos.manage_cash` as an alternative to `pos.view_sale_invoices` (`@RequireAnyPermission`), so Cash Management's Session Invoices doesn't need a second permission just to see a session's own sales. `GET /sales/:id` (`SalesService.findOneOrFail()`) returns the raw `Sale` entity plus derived `cashierName`/`customerName`/`paymentMethodName` — the raw `cashier`/`customer`/`paymentMethod` relation objects are stripped from the response (set to `undefined`, which JSON drops) so a viewer only gets display names, never a full `User`/`Customer`/`PaymentMethod` record.

`findAll()`/`exportCsv()` (`GET /sales`, `GET /sales/export`, both `pos.view_sale_invoices` or `pos.manage_cash`) share one `buildSalesQuery()` — same before-pagination-filter-building pattern as Cash Management's `buildSessionsQuery()`. `QuerySalesDto.sellAt` (Retail/Wholesale) backs the Sale Invoices page's "Sale Type" filter — it's the only sale-type distinction that exists in this schema; there's no Channel or Delivery Partner concept (no e-commerce/delivery integration built), so `findAll` deliberately doesn't accept filters for those. The list/export response now also includes `locationName` (an `innerJoinAndSelect('register.location', ...)` added alongside this).

### Sale Settings (`src/modules/sale-settings/`) and Receipt Settings (`src/modules/receipt-settings/`)

Both are single-tenant singleton tables, same `findOrCreate()` pattern as `Configuration` — `GET`/`PATCH /sale-settings` and `GET`/`PATCH /receipt-settings`, both `pos.manage_sale_settings`. `SaleSettings` is 8 plain booleans matching the Sales tab's toggles; only `sellWhenQuantityZeroOrBelow` has real enforcement (wired into `SalesService`, see above) — the rest (`allowSalesman`, `allowQuotation`, `activateKitchenTicket`, `sellBelowCost`, `taxableInvoiceB2b`, `numberDialog`, `enableWhatsappMessages`) are catalog-only, same deliberate decoupling as elsewhere in this codebase (toggleable, not yet enforced, because the corresponding feature — a salesman field on a sale, quotations, kitchen tickets, a below-cost warning, B2B tax invoices, a numeric keypad, WhatsApp integration — isn't built).

`ReceiptSettings` has 22 `show*` boolean columns (grouped Header/Items Content/Footer on the frontend via `RECEIPT_TOGGLE_SECTIONS`, a frontend-only grouping, not a backend concept), `salesNote` (free text), `commentImageUrl` (uploaded via `POST /receipt-settings/comment-image` / removed via `DELETE`, same Firebase-backed pattern as the company logo — `ReceiptSettingsService.uploadCommentImage()`/`removeCommentImage()`), and `printLayout`/`language` enums. There's no `templateId` column — like Registers' `sellLayout`, only one template exists today, so the frontend shows a single, disabled "Default" option instead of a real picker. The exact 22 toggle names/groupings and their defaults (`docs/`-less; see `receipt-settings.entity.ts`) are this build's own reasonable, standard set for a POS receipt — not verbatim labels from a specific reference screenshot, since the exact wording wasn't available when this was built; expect the user to want some renamed/added/removed once they compare against their reference.

`GET /company/branding` (public, no permission gate) was extended this session to also return `address`/`phone`/`vatNumber`/`commercialRegister` alongside `name`/`logoUrl` — all four are information that already prints on a paper receipt handed to a customer, so a cashier with no `settings.*` permission at all still needs to read them to print one. Nothing new is exposed that wasn't already going out on a printed receipt in principle.

`GET /sales` (Invoice List) filters: date range, invoice number, payment method, location (joined through `Sale.register.locationId`), customer (name/phone/code), product name/SKU (joined through `SaleLine`, `distinct(true)`'d to avoid duplicate rows from the join), and now also `sellAt` (Retail/Wholesale — the Sale Invoices page's "Sale Type" filter, the only sale-type distinction that exists; there's no Channel/Delivery Partner concept to filter by). `findAll()`/`exportCsv()` (`GET /sales`, `GET /sales/export`) share `buildSalesQuery()`, same before-pagination pattern as Cash Management. Both, plus `GET /sales/:id`, accept `pos.manage_cash` as an alternative to `pos.view_sale_invoices` (`@RequireAnyPermission`) so Cash Management's Session Invoices doesn't need a second permission. `GET /sales/:id` (`findOneOrFail()`) returns the raw `Sale` plus derived `cashierName`/`customerName`/`paymentMethodName`, with the raw relation objects stripped (`undefined`, dropped by JSON) so a viewer never gets a full `User`/`Customer`/`PaymentMethod` record just to print a name.

Also fixed this session: `GET /locations`, `GET /products`, and `GET /categories` now accept `pos.access`/`pos.manage_cash`/`pos.view_sale_invoices`/`pos.manage_promotions` (varies per route — see each controller) alongside their original permission, since several newer features (Cash Management, Sale Invoices, Promotions) need a location/product/category *picker* without owning `settings.locations.manage`/`products.access` — the same class of gap as the Cashier/Sell-Screen fix earlier in this doc, caught proactively while building those features rather than reported by a user.

### Promotions (`src/modules/promotions/`)

`pos.manage_promotions`, full CRUD (`GET/POST /promotions`, `GET/PATCH/DELETE /promotions/:id`, `PATCH /promotions/:id/status` for the list's activate/deactivate toggle) — **catalog and scheduling only, deliberately not enforced at checkout** (`SalesService` never looks a promotion up). This is the same kind of phase boundary as Registers shipping before the Sell Screen; flag it if asked, don't quietly wire it into checkout as a "nice to have" without the user asking for that specific follow-up phase.

One `Promotion` table serves both creation flows (`type: DISCOUNT_OFF_PRODUCTS | BUY_X_GET_Y`) — the fields the other flow doesn't use stay `null`, enforced per-`type` in `CreatePromotionDto` via `@ValidateIf`, and `PromotionsService.buildEntityFields()` re-derives *all* type-specific columns from `dto.type` on every create/update (including forcing the unused flow's columns back to `null`), so switching a promotion's type in an edit never leaves stale config from its old type behind. Targeting (`targetType: ALL_PRODUCTS | SPECIFIC_PRODUCTS | CATEGORIES`, and the Buy/Get sides' own `buyTargetType`/`getTargetType`) and locations (`applyToAllLocations` + `locationIds`) are plain JSON id-array columns, not join tables — there's no enforcement path to query them relationally yet, so a real join table would be schema weight with no reader; revisit if/when checkout-time enforcement is built.

Status (`SCHEDULED | ACTIVE | EXPIRED | INACTIVE`) is derived, not stored — `PromotionsService.status()`: `INACTIVE` if the manual `isActive` toggle is off, else `SCHEDULED`/`EXPIRED`/`ACTIVE` from comparing `now` against `startAt`/`endAt`. `QueryPromotionsDto.status` filters on this same logic **in SQL** (`buildPromotionsQuery()`, comparing against `NOW()`), not as a post-pagination JS filter — the same lesson from Cash Management's `listSessions()` bug, applied proactively here instead of being caught after the fact. A percentage discount (`discountValue` when `discountType === PERCENT`, on either the main discount or the Buy X Get Y "Get" side) is capped at 100 in the service (`validatePercent()`), not just the DTO's generic `@Max`, since the DTO can't express "max depends on a sibling field" cleanly with `class-validator`'s decorators.

Reused endpoints, not new ones: the Promotions form's product/category/location pickers hit the existing `GET /products`, `GET /categories`, `GET /locations` (see the any-permission note above).

### Expenses (`src/modules/expenses/`)

`expenses.access`/`create`/`edit`/`delete`, straightforward CRUD (`GET/POST /expenses`, `GET/PATCH/DELETE /expenses/:id`). `category` is a fixed 4-value enum (`RENT | SALARIES | UTILITIES | OTHER`) rather than a user-managed category table — matches every reference to expense categories seen in the Home/Reports screenshots exactly, and a category-management screen nobody asked for would be scope invented, not built; revisit as a real table if the user wants custom categories later. `locationId` is nullable — `null` means a company-wide expense (head-office rent, etc.), not tied to one branch, same "no row = applies everywhere" convention as `Promotion.applyToAllLocations`. `ExpensesService.summaryByCategory(dateFrom, dateTo)` (grouped `SUM(amount)` by category) is the one method other modules actually call — both `DashboardService` and `ReportsService` inject `ExpensesModule` for it, so the "Profit & expenses summary" figures never duplicate this query.

### Dashboard (`src/modules/dashboard/`) and Reports (`src/modules/reports/`)

`GET /dashboard/summary` (`dashboard.access`) and `GET /reports` (`reports.access`) power the Home page and the Reports page respectively — both were fully placeholder before this pass (Home was a static "welcome" card, Reports was `ComingSoon`). Both are read-only aggregation endpoints over existing tables (`Sale`/`SaleLine`/`VariantLocation`/`RegisterSession`/`Expense`) — no new domain tables beyond `Expense` above, and no writes.

**`DashboardService` trims its own response by the finer `dashboard.*` permissions** — same `*Viewer`-object pattern as `ProductViewer`, via `DashboardService.buildViewer(user)`: `dashboard.view_financial_metrics` gates `financials` (sales/profit/inventory-value/amounts-collected), `dashboard.sales_breakdowns` gates `salesBreakdown`, `dashboard.sales_insights` gates `latestSales`/`activityLog`, `dashboard.view_register_insights` gates `cashRegisters`. A section the caller can't see comes back `null` rather than omitted, so the frontend doesn't need to special-case a missing key vs. an empty one. `dashboard.access` alone (the route guard) gets an all-`null` shape — a genuinely empty dashboard, matching a role with no finer dashboard permission at all.

**Gross profit required a new cost snapshot.** `SaleLine` didn't previously store cost at all (only price/tax were snapshotted) — `SaleLine.unitCost` (nullable, for sales completed before this migration) was added, resolved in `SalesService.resolveVariantCosts()` at checkout time: a SIMPLE/VARIABLE variant's own weighted-average `cost`, or for COMPOSITE, `Σ(component cost × qty)` — the same formula `ProductsService.loadCompositeData()` already used for the product form's read-only cost display, reimplemented scoped to just the variants one checkout call needs (no cross-module call, `SalesService` already injects `CompositeComponent`). Gross profit everywhere in Dashboard/Reports is `Σ(lineSubtotal − unitCost×quantity)`, computed via SQL `SUM()`, never pulled from today's catalog cost — so a later cost change never rewrites a past sale's recorded profit, same snapshot philosophy as price/tax.

**Both services share the "filter/group in SQL, not after pagination" discipline** established by Cash Management and Promotions — every breakdown (`breakdownByDay`/`ByProduct`/`ByCategory`/`ByBranch`/`ByCashier` in Dashboard; `loadSalesVsProfit`/`ByCategory`/`ByPaymentMethod`/`loadBranchSales` in Reports) groups with `GROUP BY` server-side. One MySQL-specific gotcha both hit: `DATE(sale.completedAt)` in a raw `getRawMany()` result comes back as a JS `Date` (mysql2's default, `dateStrings` isn't configured) in local server time, not a string — both services have their own `normalizeDateKey()` helper that handles both a `Date` and a string rather than assuming `toISOString()` is always safe (a naive `.toISOString().slice(0,10)` on a `Date` would shift the date across a timezone boundary near midnight).

**`ReportsService.loadItemsBelowMinimum()`** compares `VariantLocation.quantity <= Product.reorderPoint` (reorder point is per-product, not per-variant/location — a SIMPLE product's single variant maps 1:1, a VARIABLE product's variants all share one reorder point) for products where `reorderPoint IS NOT NULL`, one row per (variant, location) — a product stocked at two locations can appear twice if both are low. Capped at 20 rows; there's no dedicated low-stock page yet (that's Stock's not-yet-built job), this is just the Reports widget.

**No new export endpoint for "Best-selling products" CSV** — unlike every other CSV export in this codebase, the Reports page already has the full `bestSellingProducts` array in hand from the one `GET /reports` call, so the frontend builds the CSV client-side (`toCsvRow` + `downloadBlob`) rather than round-tripping for data it already has.

### Purchases & Suppliers (`src/modules/suppliers/`, `purchase-invoices/`, `return-invoices/`, `supplier-payments/`)

Four modules, one subsystem. `Supplier` is a plain entity (no reference screenshot existed for it specifically, unlike `Customer` — this is a reasonable standard record, not a verbatim match to something shown); `isActive` soft-deletes it (every purchase/return/payment row `RESTRICT`s the FK, so a supplier with history can never actually be deleted). `SuppliersService.balance()` is derived on every read, never stored: `Σconfirmed purchase invoices − Σconfirmed returns − Σpayments` — same "derive, don't duplicate" approach as `Customer.totalPaid`. `SuppliersModule` injects `PurchaseInvoice`/`ReturnInvoice`/`SupplierPayment` **entities** directly (not their modules — no circular module dependency), the same cross-module entity injection pattern used throughout this codebase.

`PurchaseInvoice` and `ReturnInvoice` share a `DRAFT | CONFIRMED` lifecycle (`PurchaseInvoiceStatus`/`ReturnInvoiceStatus`) — a draft can be freely edited or deleted and never touches stock; confirming (`POST .../:id/confirm`, or `status: CONFIRMED` passed straight to `create()`) is **permanent** — no un-confirm, no edit, no delete after that (issue a Return Invoice instead of un-confirming a purchase). `invoiceNumber`/`returnNumber` ("P{YYYYMMDD}-{n}" / "R{YYYYMMDD}-{n}") are assigned only at confirmation, same "no number until it's real" convention as `Sale.invoiceNumber`.

**Confirming a purchase invoice does two things per line, inside one transaction (`applyConfirmation()`):** increases `VariantLocation.quantity` at the invoice's own location (creating the row if none exists yet there — same "no row = zero stock" convention as everywhere else), and recalculates `ProductVariant.cost` as a **weighted average across all locations combined** — `newCost = (existingTotalQty × oldCost + purchasedQty × unitCost) / newTotalQty` — because cost is one global column on `ProductVariant`, not per-location. This was verified against hand-computed expected values in the test script (0 stock @ cost 10, buy 10 @ 20 → cost becomes exactly 20; then buy 5 more @ 30 → cost becomes 23.33). Confirming a **return** invoice only decreases stock (rejecting the whole confirmation if any line would go negative, same guard style as `SalesService.applyStockDeductions()` without an "allow negative" setting) — cost is deliberately left untouched, since stock leaving doesn't change the weighted-average cost of what remains. Both reject a COMPOSITE variant as a line item outright (a composite has no stock/cost of its own to move).

`SupplierPayment` is a plain settlement against a supplier's **account balance**, not allocated to a specific invoice — matches `purchases_suppliers.manage_suppliers_payables`'s "create settlements against supplier invoices" at the account level rather than a full invoice-by-invoice payment-allocation ledger, which would be a much larger feature than what's actually described in the permission catalog.

Permission mapping across the four controllers: `purchases_suppliers.access` — read-only on all four; `.manage_invoices` — purchase invoice create/update/confirm/delete; `.record_returns` — same for return invoices; `.manage_suppliers_payables` — supplier CRUD and creating/deleting supplier payments; `.view_credit_balance` — reading the supplier-payments list (seeing balances) without being able to record one. All four backend modules were verified end-to-end (Supplier CRUD, purchase confirm with weighted-average cost math, return confirm with insufficient-stock rejection, payment recording, balance derivation) against the live dev DB — 24 checks, all passing, no leftover test data.

### Stock (`src/modules/stock-operations/`, `stock-count/`, `stock-transfer/`)

Three independent modules, none depending on the others, each owning its own slice of manual inventory adjustment (as opposed to the automatic stock moves already done by Sales checkout and Purchase/Return Invoice confirmation).

**Stock Operations** (`GET/POST /stock-operations`, `PATCH/DELETE /stock-operations/:id`, `POST /stock-operations/:id/confirm`) — a manual stock-in/stock-out voucher (`StockMovement`, `type: IN | OUT`) with a required free-text `reason` (no reason-code table — matches the "reasonable standard record" precedent set by `Supplier`). Same `DRAFT | CONFIRMED` lifecycle as Purchase/Return Invoices: a draft can be freely edited/deleted; `applyConfirmation()` moves `VariantLocation.quantity` (creating the row if absent for `IN`; rejecting the whole confirmation if `OUT` would go negative, same guard style as `SalesService`/Return Invoices) inside one transaction. Rejects a COMPOSITE variant as a line item outright — a composite has no stock of its own to move, only its components do. No cost is touched or recorded here at all (unlike a Purchase Invoice) — this isn't a purchase, just a quantity correction. Permissions: `stock.record_draft` OR `stock.manage_movements` for create/update/delete (a "can prepare but not finalize" role vs. a full-authority one); `stock.manage_movements` alone for confirm.

**Stock Count** (`GET/POST /stock-count`, `PATCH /stock-count/:id/lines`, `POST /stock-count/:id/confirm`, `DELETE /stock-count/:id`) — a full physical inventory count at one location. `create()` auto-populates one line per non-COMPOSITE `VariantLocation` row that already exists at that location (snapshotting `expectedQuantity`, leaving `countedQuantity` null) — a count covers "everything on the shelf," not a hand-picked product list like a purchase invoice, and a location with nothing stocked yet 400s with `nothing_to_count` rather than creating an empty count. `updateLines()` lets the counter fill in `countedQuantity` for any subset of lines, any number of times, while still `DRAFT`. `confirm()` sets `VariantLocation.quantity` to match every *counted* line only — an uncounted line (`countedQuantity` still null) is left untouched, not zeroed, since "not reached yet" isn't the same claim as "counted zero." All gated by a single `stock.manage_counts` (no separate "record draft" tier here, unlike Stock Operations — a count is one atomic exercise, not something one role starts and another finishes).

**Stock Transfer** (`GET/POST /stock-transfers`, `POST /stock-transfers/:id/{cancel,approve,reject}`) — a cross-location request/approval workflow, `PENDING → APPROVED | REJECTED | CANCELLED` (`StockTransferStatus`), no `DRAFT` state at all — unlike the other two, a transfer is a request the moment it's created, not something prepared privately first. `create()` requires `fromLocationId !== toLocationId`, rejects a duplicate variant within the same request, and rejects a COMPOSITE variant line (same reasoning as Stock Operations). `cancel()` is requester-only (`requestedByUserId === user.id`) and only while `PENDING`, gated `stock.request_transfer`. `approve()`/`reject()` are gated `stock.approve_transfer` — a deliberately separate permission from requesting one, so a cashier at a branch can request stock from the warehouse without being able to approve their own request. `approve()` is the only place stock actually moves: inside one transaction, decreases every line's quantity at `fromLocation` (rejecting the whole approval if any line's source stock is insufficient — the same "all-or-nothing" guard as every other confirmation in this codebase) and increases it at `toLocation` (creating the `VariantLocation` row there if absent). `reject()`/`cancel()` never touch stock. No cost is touched (same as Stock Operations) — a transfer moves quantity between two locations of the same restaurant, not a purchase.

All three modules were verified end-to-end against the live dev DB in one combined test script — 30 checks covering DRAFT/CONFIRMED transitions, composite-rejection, insufficient-stock rejection (both Stock Operations' OUT and Stock Transfer's approve), partial stock-count confirmation, and the full transfer request → approve/reject/cancel state machine with stock-movement verification at both locations — all passing, no leftover test data. A migration (`AddStockModules`) added all 6 new tables (`stock_movements`/`_lines`, `stock_counts`/`_lines`, `stock_transfers`/`_lines`) in one pass.

### Customer Payments (`src/modules/customer-payments/`) and "Pay Later" checkout

`CustomerPayment` is `SupplierPayment`'s mirror image: a plain settlement against a customer's **account balance**, not allocated to a specific `Sale` (same account-level scope decision as Supplier Payments, not a per-invoice allocation ledger). What was missing to make this meaningful — a customer previously had no way to actually owe money, since `SalesService.checkout()` always set `amountPaid = total` — is now real: `CheckoutSaleDto.isPostPayment` ("Pay Later") makes `paymentMethodId`/`amountTendered` optional (`@ValidateIf((dto) => !dto.isPostPayment)`) and, when true, requires `customerId`, requires `pos.checkout_post_payment` (checked inside `checkout()`, same fine-grained-inside-the-service pattern as the wholesale/price-override permission checks — not a route decorator), and sets `paymentMethodId: null, amountTendered: 0, amountPaid: 0` on the resulting **COMPLETED** sale — stock still moves normally, only payment is deferred. No schema change was needed on `Sale` for this (`paymentMethodId`/`amountPaid` were already nullable); the register-close reconciliation query (`RegistersService`, `SUM(sale.amountPaid) GROUP BY sale.paymentMethodId`) already ignores a null-`paymentMethodId` group naturally, so a Pay Later sale correctly contributes nothing to any payment method's expected cash/card total.

`CustomersService.balance()` (folded into the existing `toListItem()`, used by `findAll()`, the new `findOneWithBalance()` for `GET /customers/:id`, and the new `receivablesSummary()` for `GET /customers/receivables-summary`) is now real: `totalPaid = Σsale.amountPaid` (COMPLETED sales), `debitAmount = Σ(sale.total − sale.amountPaid) − Σcustomer payments` — the per-sale gap is non-zero *only* for a Pay Later sale, so an ordinary fully-paid sale contributes exactly 0 to `debitAmount`. `CustomersModule` injects the `Sale` and `CustomerPayment` **entities** directly (cross-module entity injection, the established pattern — mirrors `SuppliersModule` injecting `PurchaseInvoice`/`ReturnInvoice`/`SupplierPayment`), avoiding a circular module dependency with `SalesModule` (which already injects `Customer` the same way in reverse).

`receivablesSummary()` exists because, unlike Suppliers (a small, fully-loaded list whose "Total Outstanding" card just sums it client-side), the Customers list is genuinely paginated — summing "every customer's balance" would mean fetching the whole table. It's one pair of aggregate SQL queries instead (`GET /customers/receivables-summary`, gated `customers.view_balances`, declared before the `:id` route so Nest doesn't swallow it).

Permission mapping: `customers.view_balances` — read (`GET /customer-payments`, `GET /customers/receivables-summary`); `customers.manage_settlements` — create/delete a payment; `pos.checkout_post_payment` — the Pay Later checkout option itself. Verified end-to-end against the live dev DB (Pay Later checkout permission/customer-required validation, stock still decrementing, `totalPaid`/`debitAmount` at each step of a partial-then-full settlement, `receivablesSummary()` delta, payment removal) — 18 checks, all passing, no leftover test data. A migration (`AddCustomerPayments`) added the `customer_payments` table; no migration was needed for `Sale` itself.

### Accounting — full double-entry (`src/modules/chart-of-accounts/`, `journal-entries/`, `fixed-assets/`, `financial-reports/`)

Four modules, genuinely real double-entry bookkeeping (per explicit product direction — not a stub). **Scope boundary, stated up front**: Sales/Purchases/Expenses/Customer & Supplier Payments do **not** auto-post to the ledger — every journal entry is either entered manually or comes from Fixed Assets' purchase/depreciation postings. Building automatic posting for every existing module's checkout/confirm path would be a much larger, riskier undertaking bolted onto already-shipped, tested modules; a bookkeeper records the accounting entries by hand instead, same "manual, not integrated" scope call as Promotions not being enforced at checkout.

**Chart of Accounts** (`Account`: `code` unique, `name`, `type` one of `ASSET|LIABILITY|EQUITY|REVENUE|EXPENSE`, optional self-referencing `parentId`, `isSystem`/`isActive`) — `normalBalanceFor(type)` (ASSET/EXPENSE → debit-normal, the other three → credit-normal) is a pure function, never stored. 17 default accounts are seeded (`database/seed.ts`, create-if-missing by `code`, same idempotent pattern as system payment methods — name stays user-editable after creation, only `type`/`isSystem` come from the seed). `type` can't change after creation (`UpdateAccountDto` omits it) since retyping an account with existing postings would corrupt every report's grouping. `remove()` blocks deleting a system account, an account with children, or one with any `journal_entry_lines` row (a raw-SQL count check, not just relying on the FK's `RESTRICT` to surface as a friendlier 400 than a raw driver error).

**Journal Entries** (`JournalEntry`/`JournalEntryLine`) — `DRAFT | POSTED`, the same lifecycle shape as every other DRAFT/CONFIRMED entity in this codebase, but journal-entry-specific: `create()` is **always** DRAFT (no create-with-status shortcut like Purchase Invoices; a manual entry is meant to be built up before posting), a separate `POST .../:id/post` validates every line has exactly one of `debit`/`credit` non-zero and that Σdebit === Σcredit before assigning `entryNumber` ("JE{YYYYMMDD}-{n}", same same-day-counting approach as `Sale.invoiceNumber`) and flipping to POSTED. A posted entry is **never edited or deleted** — only reversed (`POST .../:id/reverse`, `accounting.manage_journal_entries`): creates a brand-new POSTED entry with every line's debit/credit swapped, `reversalOfEntryId` pointing at the original, memo `"Reversal of {entryNumber}"`; rejects reversing an already-reversed entry (one reversal per entry) or a DRAFT. `postSystemEntry()` is the entry point other modules (Fixed Assets) use to post programmatically-built entries directly, skipping the DRAFT step entirely since the caller has already fully computed and validated the lines.

**Real bug caught and fixed before shipping**: `create()`/`update()`/`reverse()` each originally ended by reading the just-written row back through `this.entryRepository` (the ordinary, non-transactional repository) from *inside* the surrounding `dataSource.transaction(async (manager) => {...})` callback — since that repository uses a different connection than the transaction's `manager`, the row wasn't visible yet (uncommitted), throwing `EntityNotFoundError` for a brand-new row, or worse, silently returning stale data for a row that already existed pre-transaction (the `update()` case). Fixed by reading through `manager.findOneOrFail(...)` instead in all three spots. Caught by the write-up-front test script's first failing run, not by inspection — a good reminder to actually grep for this pattern (`this.xRepository` used for a read *inside* an open `manager` transaction) on any future module that mixes a transaction with a "return the fresh row" convenience read.

**Fixed Assets** (`FixedAsset` + `FixedAssetDepreciationEntry`) — straight-line depreciation only (`(purchaseCost − salvageValue) / usefulLifeMonths`), no declining-balance/units-of-production methods, a deliberate v1 scope match with how narrowly `Expense.category` and other "reasonable standard record" entities are kept elsewhere in this codebase. `create()` optionally takes `paymentAccountId` — if given, immediately posts a purchase journal entry (debit the asset account, credit the payment account) via `postSystemEntry()` in the same transaction as the asset row; omit it to register an asset with no accounting entry (already recorded another way, or historical data being migrated in). `recordDepreciation()` computes the straight-line monthly amount by default (overridable, e.g. for a partial period), caps it so accumulated depreciation never exceeds the depreciable base, rejects a second run for the same `periodDate` on the same asset, rejects depreciating a disposed asset, and posts debit Depreciation Expense / credit Accumulated Depreciation. `dispose()` is a pure status flip (`status: DISPOSED`, `disposedAt` set) with **no** gain/loss-on-disposal journal entry — computing that needs a sale/scrap proceeds figure this app doesn't model, so it's flagged here as a deliberate omission rather than guessed at. `accumulatedDepreciation`/`bookValue` are always derived from `Σdepreciation entries`, never stored redundantly.

**Financial Reports** (read-only, no new tables — same shape as the Dashboard/Reports rollup services) — every report only ever looks at **POSTED** journal entries, exactly like every other "DRAFT is invisible to reports" rule in this codebase. `trialBalance(asOf?)` places each account's net (`Σdebit − Σcredit`) into whichever column it's actually on (positive → debit column, negative → credit column), independent of the account's "normal" side — a revenue account with a net debit (e.g. fully reversed) still shows under debit, not forced into credit; rows with zero activity are dropped. `generalLedger(accountId, dateFrom?, dateTo?)` computes a running balance in the account's normal-balance direction. `incomeStatement(dateFrom?, dateTo?)` is `Σrevenue credit-normal balances − Σexpense debit-normal balances`. `balanceSheet(asOf?)` folds **all** undistributed net income since inception (not just the current period — there's no period-close-to-retained-earnings step in this v1) into Equity as a "Net Income" line, which is what actually makes Assets = Liabilities + Equity hold without that step; flagged in the code as a deliberate simplification, not an oversight.

**Setup Guide** (`GET /accounting/setup-guide`, `accounting.view_setup_guide`) is a live overview, not a checklist — most "onboarding steps" (e.g. "reviewed your chart of accounts") can't actually be detected as done, so rather than fake completion states it just returns real counts (accounts total/active, journal entries total/draft/posted, fixed assets total/active) plus whether the trial balance currently balances, computed with a few raw aggregate queries on `ChartOfAccountsService` (kept there rather than a new module, since Chart of Accounts is the natural "base" of the four).

Permission mapping across the four controllers: `accounting.access` — read on accounts/journal entries/fixed assets (mirrors `stock.access`'s role as the module's general read gate, despite its catalog description narrowly saying "view chart of accounts"); `accounting.manage_chart_of_accounts` — account CRUD; `accounting.record_journal_entries` — create a draft + post it (matches the catalog text exactly: "create and post"); `accounting.manage_journal_entries` — edit/delete a draft, or reverse a posted entry (matches "edit, reverse, or delete"); `accounting.manage_fixed_assets` — fixed asset CRUD, recording depreciation, disposal; `accounting.view_financial_reports` — the four report endpoints; `accounting.view_setup_guide` — the setup guide endpoint. All four modules verified end-to-end against the live dev DB in one combined script — chart-of-accounts CRUD + system-account locks, journal entry create/update/post/reverse with real balance validation (including the transaction bug above, caught by this very script), fixed asset purchase-posts-a-journal-entry + straight-line depreciation + duplicate-period/disposed guards, and all four financial reports (trial balance debit=credit, general ledger running balance, income statement, balance sheet assets=liabilities+equity) — 40 checks, all passing, no leftover test data. A migration (`AddAccounting`) added all 5 new tables (`accounts`, `journal_entries`, `journal_entry_lines`, `fixed_assets`, `fixed_asset_depreciation_entries`) in one pass.

### Digital Menu (`src/modules/digital-menu/`) — public, no session

The first genuinely public *business-data* endpoint in this app beyond `company/branding` — a customer scanning a table QR code has no session cookie at all, so both routes use `@Public()` (bypasses the global `JwtAuthGuard` entirely) and carry no `@RequirePermissions`/`@RequireAnyPermission`. Built as its own module specifically so nothing about it could weaken the already-shipped, tested `ProductsController`/`CategoriesController`/`LocationsController` — it reads their **entities** directly (`Product`, `Category`, `Location` — cross-module entity injection, the established pattern) rather than adding public routes to those controllers or reusing their (authenticated) services.

`GET /digital-menu/locations` — id/name only for every `isActive` location, backing a location switcher; same "public and permission-free on purpose, nothing sensitive" reasoning as `company/branding`. `GET /digital-menu?locationId=` — resolves to the given location (404 if missing/inactive) or `isDefault` if omitted, then returns `{branding, location, categories, products}` in one call. `categories` is deliberately flat (`{id, name, parentId}`) — the frontend already has tree-building utilities from Category Management, no need to duplicate that server-side. `branding` reuses `CompanyService.findOrCreate()` (now `exports: [CompanyService]` from `CompanyModule`, a small additive change) narrowed to name/logo/address/phone, the same fields `company/branding` exposes.

**Product inclusion rule**: a product needs `isSellable: true` *and* at least one variant with a non-null `retailPrice` at the resolved location — same "no price at location" business rule `SalesService` already enforces at checkout, just read-only here. A product with zero priced variants at that location is silently excluded rather than shown with a missing price. **Stock rule**: an out-of-stock variant (`Product.trackQuantity` on and `VariantLocation.quantity <= 0`) stays on the menu with `inStock: false` instead of disappearing — closer to how a real restaurant menu marks something "Sold Out" than hiding it, and lets a customer still see it's a thing the kitchen makes.
